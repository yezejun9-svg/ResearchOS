# 15 · 每个新项目的开工规则：先本地与调研，判断后复用源码，再适配验证

## v2.4 当前仓库与普通任务的适用范围

新项目和既有项目新增大能力执行完整流程；当前ResearchOS走18的EXISTING_CONTINUATION，保留永久身份及已有资产。普通小修复复核已有本地记录和受影响代码，不为每条聊天重新跑三来源全量选型。研究由当前问题驱动；没有候选优势时保持现状。Jev reuse_selection及整仓/模块/依赖的真实采用要求继续完整生效。

规则版本：1.1；纳入实施包2.4.0。依据用户2026-10-01的最终澄清：不是一味clone，而是判断值得采用的实现，再获取并修改源码；Jev用于辅助判断。适用于ResearchOS自身，以及建成Agent以后在授权范围内实施的每个项目。既有项目新增大能力同样适用；小修复读取已有记录并检查变化，不重复无关调研。

## 1. 顺序与执行原则

**需求与本地盘点 → 针对缺口调研 → 检查候选源码并做有界验证 → Jev提供结构化建议 → 硬门检查和独立接受 → 获取选定代码并适配 → 实际验证。**

1. 先用本地已有代码、依赖、工具、技能和历史判断；不因发现新项目就替换已能工作的实现。
2. 针对实际缺口研究现成方案，判断是否比保留现状更合适。README、热度和Jev高分均不能单独证明适合。
3. 判断值得采用后，直接以选定仓库或源码模块为基础修改，也可以使用已满足需求的库/SDK。不能只看设计，然后另写一套相同能力。
4. 不值得采用、需要补证、没有资源验证，都是允许的结果。只有有证据的能力缺口才新写最小必要部分。

衡量收益看需求覆盖、实际通过情况、适配成本、后续维护和可回退性，不看clone数量或采用项目数量。普通技术选择在既有授权内自主推进；独立接受是证据与职责分离，不要求每个库都重新向用户请示。

## 2. 第一步：需求与本地盘点

先确认项目身份、工作目录、Git状态和已有修改，读取适用说明，再把目标拆为带验收条件的能力清单。在授权范围内检查：

- 当前仓库模块、组件、测试、命令、锁文件、依赖、构建和部署入口。
- 已保存的开源源码、模板、CLI、桌面壳、SDK及工具安装；记录真实路径和版本。
- 已有skills、插件、MCP/连接器及能力探针；只读取能力和凭据引用，不采集秘密内容。
- 已有调研、接受/拒绝记录、失败实验，以及本项目可合法使用的通用模块。

优先使用`rg --files`、目标文件搜索和实际版本命令。不扫描未授权项目；新项目不会自动获得其他私有仓库或账户的权限。

保存LocalInventory为现有Artifact，包含时间、环境、授权范围、路径、revision/hash、dirty状态和证据。条目区分FOUND、NOT_FOUND、NOT_CHECKED、NOT_ACCESSIBLE。无法读取用户PC而只检查当前会话目录时，明确检查范围；不能把未访问等同于没有。

## 3. 第二步：调研与两阶段源码获取

围绕能力缺口、现有候选的来源和兼容性做有界核查，优先官方仓库、源码、发行说明及可复现执行。X讨论、star数和宣传用于发现候选，不能代替代码与运行证据。

**检视阶段的临时clone不等于采用。** 可以先在隔离的候选目录clone/fetch固定revision，检查实现和许可证，做针对性构建、接口或关键能力探针。此时不替换主工程、不改变正式依赖锁，也不因“已经下载了”就认定必须采用。检查安装脚本、依赖及所需权限后，在授权和预算内运行必要验证。

**采用阶段才进入产品代码。** 只有经过下述判断与接受的具体能力，才将选定源码整仓fork、按模块集成或固定依赖，并落实适配、来源保留、验证和回退。临时下载路径与正式采用路径分别记录。

比较至少包含：需求覆盖与缺口、实际源码入口、许可及子目录差异、目标平台/运行时、与本地架构和数据的兼容性、已执行/未执行测试、适配范围、维护负担和退出成本。相应证据未知时标明未知，不用估计分数补全事实。

已有新鲜且相关的调研可以复用，但记录URL、抓取时间、固定revision/hash和适用范围；不同版本、平台或用途定向补查。初始最多深入比较两条覆盖关键能力的路线，每条最多一次针对性修复；扩大范围须有具体缺口。网络/账户/额度受阻记录RESEARCH_BLOCKED或覆盖PARTIAL，不能据此认定不存在现成方案。

## 4. 第三步：Jev建议、硬门和独立接受

把同一能力要求、现状基线、候选源码/实测证据、已知缺口和成本假设交给Jev，要求结构化的建议、依据引用、拒绝理由、待补证项与弃权理由。采用选择的输入、资格、回执和验收细则由16及机器合同定义；本用途的精确task_type为`reuse_selection`。

Jev是判断信号；它不自动批准clone、外部执行、扩大权限、修改验收或发布。高分不能覆盖许可不满足、平台不支持、测试失败、证据过期/缺失或用户约束。模型置信度不是现实成功概率，不能把排序分数当作确定收益。

使用现有SHADOW/ADVISORY/BOUNDED_AUTO及精确用途资格：源码采用判断不能继承上下文筛选、Goal或其他用途资格。未取得本用途资格时，真实调用只作为SHADOW/ADVISORY；具备BOUNDED_AUTO资格也仍受动作范围、预算、授权和确定性硬门限制。模型、rubric、语言或用途变化须按既有规则重新核对资格。

实际未调用时必须记录NOT_RUN；账户、网络或资源阻断时记录BLOCKED及原因。fixture仅证明协议与拒绝路径，不能声称“Jev已经比较过候选”。保存输入hash、来源revision、实际provider/model/rubric、模式、原始响应引用、建议、耗时及费用；未知费用为null。

独立接受检查证据是否完整、实际验证是否达到本次准入条件、是否符合许可/平台/项目约束，以及改动和回退是否可执行。提出候选的一方不能自行修改硬门使其通过。常规方案可由既有独立验证身份在授权内接受；只有本来就需要用户授权的动作才请求授权。无合格候选时允许不采用，不能为了给Jev建议凑一个结果而强行集成。

## 5. 第四步：逐能力选择具体复用方式

采用裁决正文由`contracts/adoption.schema.json`的SourceCandidatePayload/AdoptionDecisionPayload定义，存为现有Artifact并关联既有DecisionReceipt，不新增领域实体。决定同时说明“是否采用”和“怎样采用”，不能只写“借鉴”。

| 裁决 disposition | 含义 | 后续 |
|---|---|---|
| ADOPT | 当前证据与准入门支持选定方案 | 固定源码/依赖并按接受的范围实施 |
| REJECT | 当前候选不合适或硬门失败 | 保存拒绝依据，保留现状或比较其他候选 |
| WATCH | 暂不采用，值得关注的条件尚未成熟 | 记录重新评估条件，不进入正式实现 |
| INCONCLUSIVE | 缺关键证据或验证资源，尚不能判断 | 明确待补证与阻塞，继续独立支路 |

正式实施的reuse_strategy沿用REUSE_LOCAL、ADOPT_UPSTREAM、ADAPT_UPSTREAM、CUSTOM_GAP；无实施方案时为null。reuse_extent明确代码实际引入范围，不以策略名称掩盖整仓与模块的差别：

| 范围 reuse_extent | 适用情形 | 必须落实的结果 |
|---|---|---|
| LOCAL | 本地实现已满足或可有限修改 | 实际路径、固定版本、受影响验证；不重复clone |
| WHOLE_REPOSITORY | 上游整体架构与核心能力适合 | 整仓fork、来源commit、主工程目录、保留/修改清单、上游跟进和回退 |
| MODULE | 只有特定源码模块适合 | 来源文件/模块、对应commit、许可与归属、接口和本地补丁 |
| DEPENDENCY | 标准库/SDK/工具接入已满足能力 | 固定依赖、真实适配入口、兼容测试与升级策略 |
| GAP_ONLY | 已证明无法合理复用的最小缺口 | 最小新增范围、继续复用部分、验证和撤回方法 |
| NONE | 当前没有批准引入代码 | 拒绝/观察/补证理由和后续条件 |

每条裁决关联能力/需求、本地盘点、候选比较、Jev实际状态、硬门与独立接受。原ReuseDecisionPayload仅表示正向实施计划，必须通过adoption_decision_ref引用已接受的采用裁决。不能把候选全部装入主工程后再决定，也不能将非采用裁决伪装成CUSTOM_GAP。

正式采用固定commit/版本及内容hash，记录原始URL、子树许可证和版权、上游remote、补丁范围、下游接口、升级方式及可回退基线。复制代码保留相应来源和许可，第三方资产单独核查；不得用浮动latest替换已验证组合。

适配完成需实际运行原有关键测试和本项目受影响验收，检查CLI/Desktop、数据与接口兼容，保存源码diff及回执。clone成功、能安装或能启动不等于功能完成。存在可用源码时，应在其上修改或直接集成；无理由地重写成熟终端、桌面壳、模型SDK、存储、日志、解析器或打包器不通过。

## 6. 最小缺口自研的准入

CUSTOM_GAP必须包含具体能力及验收条件、本地结果、已比较方案及拒绝理由、源码/实测缺口证据、最小新增文件或模块范围、继续复用哪些部分，以及验证和回退方法。需要写领域逻辑、适配层和测试时明确这些新增代码的用途，不把适配误称为整套自研。

“自己写更干净”“暂时没找到”“没有账户”不足以批准从零实现。某方案失败只证明该方案在该条件下失败；资源不足保留阻塞，不自动转为自研。确无合格候选是合法结果，同样要留证据。

## 7. 做成Agent内置流程与可见体验

ResearchOS的`init`、Desktop“新建项目”和项目内研究能力进入同一流程。阶段仍为LOCAL_INVENTORY→RESEARCH→REUSE_DECISION→IMPLEMENTATION；源码检视、Jev建议、硬门、采用策略和验证是阶段内部证据，不新增或替换TaskStatus。

项目可先建立身份、最小元数据和候选工作区；受限调研/资格样机可进行，正式采用按独立接受的逐能力决定推进。CLI/Desktop读取同一Artifact、DecisionReceipt引用与EventEnvelope，不复制一套决策状态。界面显示为什么采用/拒绝、Jev是否真实运行及其模式、尚缺什么、具体源码差异和验证结果；不把建议展示成“已经批准”或“已经通过”。

初始化时将本规则作为版本化项目策略引用带入所有新会话与子Agent的ContextBundle。已有AGENTS/项目说明先读并保留，冲突按用户指令与适用范围解决，不覆盖全局配置。新版本/输入变化只重开受影响判断，不每轮重新全盘选型。

## 8. 实施阶段、验收与交接

W00/W01先执行本规则完成ResearchOS自身盘点和源码路线验证，不新增W01对W11的依赖。若已有授权Jev资源，可记录预资格的真实ADVISORY建议；此阶段仍由确定性检查和独立评审接受有界技术路线。缺服务时记录Jev BLOCKED/NOT_RUN，推进调研、源码检查、资格样机、接口骨架和无依赖工作；不能伪造Jev通过，也不能宣称完整判断流程已经交付。

W04只做初始化状态机、本地盘点和记录协议；W07/W08接齐研究与复用决定，W08先冻结候选证据、Jev建议及接受/拒绝的fixture协议。W11完成真实Jev适配、用途资格评测与安全降级；W14将真实判断和源码采用/拒绝接入完整项目演示。W08无需等待W11完成即可实现并测协议，但fixture不能替代W11/W14真实证据。

沿用B01/A01、B02/C05、A08和P06/A13等现有验收映射，细则见16及contracts；不新增任务或假定全部自动权限已获得。验收覆盖本地足够、整仓适配、模块/库复用、候选不合适、证据/服务缺失、高分但硬门失败、真实最小缺口和适配后回归。未闭合真实Jev与源码适配/拒绝证据，不能宣称建成Agent已具备完整的自主判断复用能力。

交给下一位Agent的最少记录：本地盘点、候选来源及验证比较、Jev调用或缺失状态、逐能力裁决与独立接受、实际源码/依赖锁与diff、验证和回退回执。放入W02已确定的执行目录，不另建第二套项目管理系统。最终展示所采用实现节省了什么、改了什么、证实了什么；没有测量不编造节省比例。

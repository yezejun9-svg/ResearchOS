# Private evidence persistence and authority follow-up

Read-only inspection of the same frozen `c40b7cfb44ddef19f9966ab81e1eef7c991beafb`; no native/test execution or payload construction.

**Persistence is not yet sufficient for a reviewable formal receipt.** `prepareC20Private` creates the CanaryStore under `t.TempDir()/private-c20` (`evolution_holdout_test.go:33-34`). Input, label and complete private proof blobs are written to that store. The helper's only persisted result from `c20PrivateConclude` is a benefit aggregate plus a private proof hash (`164-170`); `evolutionFixture.run/save` writes public execution/acceptance/candidate records to `W16_EVIDENCE_DIR`, not the private input/label/proof bodies. Those bodies disappear with the temporary directory. A hash remains a binding identifier but cannot let a later verifier recompute the private scores. The formal fixture evidence needs retained protected-store blobs and controlled references; ordinary repository evidence should continue to contain only safe aggregates/references. This does not require publishing private questions or labels.

**Missing-proof gates are connected at both decision points.** `verifyEvolutionObservation` calls `evolutionRecordValid`; `START_CANARY` calls `evolutionAccepted`, which calls the same validator. For a registered candidate, `evolutionHoldoutVerdict:286-288` refuses an absent evaluated record; `293-306` re-reads all three protected bodies and checks hashes. A missing or altered proof therefore blocks both acceptance and subsequent use of that acceptance in START_CANARY according to source. Existing missing/tamper test source exercises the latter gate only. No independently executed result is asserted here.

The optional legacy branch at `evolutionHoldoutVerdict:282-284` returns no holdout only when there is no HOLDOUT_FROZEN record. The migration's `evolution_journal_noupdate` and `evolution_journal_nodelete` triggers make that record append-only under ordinary database operations. For an already registered candidate, deleting its protected proof body does not enter the legacy branch.

**Current authority is checked at entry, but not at every later decision.** Register and Evaluate authenticate the supplied token and call `protectedAllowed`, which requires current OWNER/VERIFIER role plus a restricted project grant. Proof registration through `RegisterProtectedArtifact` checks current authority again after provider I/O. However, the final transaction writing HOLDOUT_EVALUATED (`250-266`) only rechecks the candidate plan/status and absence of a previous evaluation. It does not reauthenticate the verifier or recheck its authority relationship. Later `evolutionHoldoutVerdict` only compares stored verifier IDs; neither it nor `evolutionPrivateBytes` loads that principal's current revoked status, role or restricted grant. Artifact `effective` checks version/validity/lineage and body integrity, not the producer's current grant. Thus these functions alone do not establish current verifier authority after revocation. Whether historical proof remains usable after producer revocation must be decided against the governing contract; this review does not silently substitute receipt-verifier checks for holdout-producer checks.

**Release aliases are not covered by the new independence predicate.** Register resolves authorRoot and verifierRoot, but rejects the release actor by `p.ID == h["release_principal"]` (`135`). An independent release authority root is already used elsewhere by `createSystemCandidate`; the new holdout registration does not compare it. Evaluate and later proof validation also do not repeat the author/release root comparison. If the intended rule is that release authority may not select or label its own holdout, use the same root-level rule at this boundary. This is a source gap, not an executed impersonation result.

The impossible Gain predicate in the separately frozen initial review remains the definite correctness blocker. This follow-up adds no whole-C20, GLOBAL-run or LIVE qualification.

# Fresh-attempt follow-up input map

READONLY_DISCOVERY_ONLY. This map is not a Source implementation card, approved design, new attempt preparation, model consent or actual operation. B/C/STOP/D architecture is under independent review at CP498. Source A and historical22 fixture own the only two active construction cards.

The current schema24 can store multiple immutable plans per runtime because runtime_qualification_plans primary key is (project,task). runtime_bindings has one immutable row per (project,runtime), and qualification_runs one per (project,task). The next-attempt design must account for all three separately.

Concrete coupling points:

- internal/domain/runtime_qualification.go:163 unconditionally inserts runtime_bindings before the plan. Existing registerRuntimeQualificationPlanTx cannot create a second plan for the same runtime without a bounded exact-existing-binding reuse branch. Never use INSERT OR REPLACE or overwrite the immutable binding. Reuse must verify the exact owner/current root, technical/profile identity and full original row.
- internal/domain/client_runtime_setup_windows.go:196 and runtime_qualification_execution_windows.go:253 use QueryRow(project,runtime) without an attempt identity/order. They become ambiguous after a second plan. New selection needs a checked append-only lineage and explicit task identity; ORDER BY rowid alone is not an authority record.
- client_runtime_setup_windows.go:368 also queries by runtime and :398 requires that selected task equal each original executor grant. All historical qualification grants must instead be verified against their own exact task/run/epoch and immutable plan. Ordinary mu_turn grants must retain their original dispatch/profile checks.
- runtime_qualification_confirmation_windows.go:145 reports only SETTLED as EXECUTION_SETTLED; a legitimately closed FAILED Run still appears UNRESOLVED today. A future status addition must distinguish terminal consumed failure and bind its validated closure receipt. It cannot map arbitrary FAILED or Cancelled evidence to permission or allow retry.
- apps/desktop/main/lib/desktop-management.js prepare() only retires unconsumed expired intents. Its status() accepts a fixed state set and retains confirmSent. IPC/preload/UI currently expose only current/prepare/confirm/status. A fresh-attempt action therefore needs explicit private wiring and its own intent, with the old consumed identity preserved as history. The old CONFIRM cannot be redirected to a new request.
- apps/web/src/workbench.jsx DesktopQualification disables prepare whenever a consumed request exists. A separate action must display prior terminal outcome/cost and request a new preparation; the existing one-call confirmation remains a separate deliberate action.
- internal/domain/operations.go:219 uses origin_problem_id + candidate_id + input_hash to find NoProgressRecord. Creating a fresh Task with the same qualification inputs naturally reuses its existing failure/progress counters. Do not silently vary those inputs to obtain a fresh zero-count record. Any deliberate new input identity needs explicit lineage and must retain the ancestor counters/stop policy rather than bypass them.

Candidate decision for later independent design review: reuse the same active Goal/current budget ancestry and immutable runtime/profile, create a new Task+context+plan in one serialized zero-model transaction, and use append-only idempotency/Artifact records in existing schema24 for attempt sequence and prior closure linkage. This is only a candidate; exact immutable format, race serialization, legacy first-attempt derivation, startup reconciliation and all readers still need a reviewed contract before implementation. No schema25 migration should be added implicitly to obtain this feature.

Acceptance cuts needed beyond the architecture: existing binding row byte-identical; all three runtime-wide plan lookups repaired; historical executor grants still valid; concurrent different intents cannot create two next sequence numbers; same intent is idempotent; first-attempt legacy behavior unchanged; consumed FAILED history is shown without authorization; prior NoProgressRecord and UNKNOWN money preserved; tightened ancestor policies block; zero dispatch/calls during preparation; separate new request confirm only once; old CONFIRM always addresses its own old request.

## Trust and two finite build phases

A caller-supplied plan hash is integrity, not approval. Choose one operation-specific dedicated executable whose private link-time grant pins externally accepted inputs. No signing program, signing key, registry, environment override, runtime grant file, force flag, test bypass or caller callback is introduced. Trust is the declared same-SID Owner/operator review/build workflow and pinned build output, not protected holdout or resistance to a malicious same-user administrator rebuilding arbitrary code.

Preflight creates backup and a final plan; final plan bytes cannot be approved before they exist. Resolve that dependency explicitly with two builds of the same accepted Source:

1. **PREFLIGHT_ONLY build** contains a nonempty grant for one exact canonical preflight subject/proposal document, its independent preflight review, public evidence manifest and Root preflight scope. It can run only that proposal's real preflight and inspect its own results. It has zero terminate authority. Preflight output includes the canonical final plan, backup manifest/census and a complete immutable evidence manifest.
2. Root and an independent reviewer inspect those actual preflight outputs. Only a later authorized **STOP_ONCE build** contains the final plan SHA, complete preflight evidence manifest SHA, independent stop acceptance/review SHA and Root actual-stop scope SHA. It can run commit for precisely that operation and inspect that journal; it cannot refresh a plan/backup or run another preflight. It is a new build artifact, not a mutation of the already pinned preflight binary.

The two grants have different build identities and grant digests, share operation ID and exact subject, and the STOP_ONCE grant includes the preflight grant digest and preflight executable digest. No hash cycle: preflight proposal SHA excludes measured outputs; STOP_ONCE pins final output SHA and predecessor build; neither grant embeds its own executable digest. The external build manifest binds accepted Source, toolchain/flags, exact grant bytes/digest and resulting executable SHA. Future operational review pins that output executable before use. A new STOP_ONCE executable cannot treat a caller's claimed review as accepted merely because its JSON is self-consistent.

## Loading and immutable API

`internal/ownedcorestop/contract.go` declares package-private `var compiledOperationGrantBase64 string` with default empty. Root's reviewed build invocation sets it with Go `-ldflags -X researchos.local/research-os/internal/ownedcorestop.compiledOperationGrantBase64=<canonical-base64>`. This is a link-time payload in a dedicated binary; no CLI/env/config setter exists. Fixtures use the same real build option and production code. Do not mutate it from test Go code and call that a compiled-grant test.

`loadCompiledOperationGrant() (operationGrant, error)` is package-private, strict, bounded (at most64KiB decoded), and cached once. Empty/noncanonical base64, duplicate JSON keys, unknown fields, trailing data, invalid digest/path/identity/time fields or unsupported kind returns `STOP_GRANT_UNCONFIGURED`/`STOP_GRANT_INVALID` before DB, backup, process-handle or output-journal operations. The struct's fields are private. `newCompiledOperator()` (or the corresponding existing command constructor) takes no authority argument. Its preflight/commit/inspect methods always load that grant internally. There is no exported `SetGrant`, grant map, accepted bool, injected checker or callback. Internal pure validation tests may decode bytes, but production entrypoints obtain authority only from the compiled payload.

All caller arguments select files matching already pinned inputs; they supply no permission. `--expect-plan-sha256` remains an extra equality check and must equal the compiled expected SHA. It cannot be used with an unconfigured binary. A default/unconfigured CLI returning denial is safe-disabled behavior only; it is not complete usable Source acceptance. Non-Windows remains unavailable.

## Exact grant fields and binding

Shared required fields are schema `researchos.owned-core-stop-compiled-grant.v1`, grant_kind, operation_id, issued_at/not_before/expires_at, purpose `EXACT_RETAINED_CORE_CRASH_STOP`, trusted_operator_sid, full native canonical data-root/database identity, private operation-directory canonical path plus identity, target Core PID/creation100ns/image canonical path+file identity+SHA, exact Desktop parent PID/creation/image SHA, Host public identity/hash and current Owner principal/root identity/hash, old project/task/run/runtime/epoch/request/dispatch tuple, required proof-class IDs, ruleset version, and allowed action count. Creation times use decimal strings, never float JSON numbers. Pin public authoritative document digests without including credential/private-key contents.

PREFLIGHT_ONLY additionally requires `proposal_sha256`, `preflight_scope_sha256`, `preflight_review_sha256`, `historical_evidence_manifest_sha256`; allowed actions are preflight/inspect and terminate_count=0. Proposal fixes output names, schema fingerprint expectation, native closure requirements, permitted unresolved subject and all input evidence references. It cannot contain a wildcard subject, any-root selector or future acceptance switch. Preflight must revalidate every required fact and may return unavailable; a valid grant is not a proof substitute.

STOP_ONCE additionally requires `plan_sha256`, `preflight_manifest_sha256`, `stop_review_sha256`, `root_operation_scope_sha256`, `historical_evidence_manifest_sha256`, `preflight_grant_sha256`, `preflight_executable_sha256`; allowed actions are commit/inspect and terminate_count=1. Each digest is a nonempty exact SHA256, not zero/placeholder/prefix. The compiled grant pins both final plan and its separate review/scope/evidence, and all subjects must agree across them. The final plan cannot add another native subject or another accepted proof class. The required class list initially remains the independently accepted strict classes; NEVER_JOB_AUTHORIZED cannot appear until separately accepted architecture/source and a later operation scope explicitly select it.

Document files referenced by the grant are opened through retained non-reparse file handles with size bounds and exact byte hashes; decode strictly and compare schema, operation, subject, acceptance status, allowed action and expiry to the compiled grant. A matching hash is insufficient if document semantics conflict. Input indexes must resolve all member digests; missing required evidence is unavailable. Source/runtime validation still checks the real current SID, authority, native handles, schema/census and closure proofs; no grant can override a failed fact.

## Lifetime and one-action rules

Each grant has an explicit validity interval of at most30minutes. Validate wall-clock interval at initialization, after long preflight/backup/lock waits, before BEGIN, and immediately before TERMINATE_INTENT. Within one invocation also use a monotonic deadline derived from the initially remaining interval, so a backward wall-clock change cannot lengthen that invocation. Expiration before termination means zero action and orderly reservation release. Expiration after a single action cannot authorize a retry: finish bounded native wait/postflight or record UNKNOWN. Expired inspect can read existing immutable journal receipts for this compiled operation only, with no new backup, DB connection, native probing, grant renewal or action.

Acquire an exclusive operation-directory lock before any journal creation/action; hold its non-reparse directory identities and private ACL checks until return. Plan, preflight manifest, BEGIN and TERMINATE_INTENT bind both grant digest and final plan SHA. Concurrent invocations with the same operation cannot both create an intent; a different compiled grant/plan pointing to that journal conflicts. Existence of TERMINATE_INTENT permanently consumes this operation's one action, even when the process died before calling TerminateProcess. There is no interpretation that missing NATIVE_EXIT permits another attempt.

The STOP_ONCE commit validates the grant and full immutable preflight chain, retains the exact target and parent handles, takes the reviewed SQLite barrier and checks current authority/census, then writes+flushes BEGIN and TERMINATE_INTENT with grant digest before the one TerminateProcess. Use the original retained handle for identity recheck, termination and wait; never reopen by PID after the barrier. Exact target already exited means zero termination and a separate observation. PID reuse/image/root/Owner/Host drift, unknown child/effect, stale backup or any evidence mismatch yields zero termination. Completed replay returns the same immutable outcome. `inspect` is observation-only and cannot call commit internally. A lost/torn journal or intent without reliable outcome stays UNKNOWN and cannot be repaired by deleting files or rebuilding the same grant.

## Nonempty real Source-fixture acceptance

Source fixtures must launch only their isolated disposable Core fixture, obtain its actual identity, prepare reviewed synthetic input documents in a new private root, build a **nonempty PREFLIGHT_ONLY executable**, and invoke its real CLI preflight to create an actual SQLite online backup/census/final plan. They then freeze the fixture review/scope/manifest, build a separate **nonempty STOP_ONCE executable**, and invoke the real commit and inspect CLI. This uses no current product data or actual process identity. The fixture review is labeled synthetic and is compiled only into that fixture-specific binary; it cannot authorize any other subject.

The full positive chain must reach one real native termination, original handle wait, postflight DataRootLease and exact logical baseline, with one immutable outcome. Run the existing S209/S216 reservation/drift cuts through the grant-aware path as well. Negative cuts cover absent/empty/malformed grant, caller replacing every JSON/hash while binary pins remain fixed, proposal grant attempting commit, final grant attempting preflight, changed scope/review/evidence/member, mixed subject, expiry before/after wait, same-operation concurrency, intent crash/no-retry, image/PID/root/Owner drift and repeated inspect. Source acceptance requires both positive nonempty E2E and negative controls; safe-default denial alone is insufficient.

No current Root actual pins are installed by this design or Source fixture card. Future grant materialization, two dedicated builds, independent output review and actual invocations require their own exact Root scopes. Formal increment0.

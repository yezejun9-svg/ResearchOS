## Draft semantics and resource limit

The frozen v2.4 `contracts/client.protocol.schema.json:497–520` permits `start_as_draft`, and `StartGoalResult` at 1647–1681 permits `goal_status=DRAFT`. It also requires `snapshot`, whose `model_config_ref` is a nonempty required string at 856–859 and 990–1003. The registered Goal source contract `goal_source_scope_codex.json` explicitly requires a unique current workspace/model resolver before project-level business writes, while specifying that Draft writes a real Goal/Requirement/session association only, with no Task/Run/dispatch; non-draft alone enters runtime purpose/qualification gates. Main implements this split at `client_protocol_goal.go:56–75`: Draft skips `FreezeClientTaskInputs`, creates Goal, and returns before Task/AdmitTurn. `client_protocol_goal_test.go:77–108` checks DRAFT with zero Task/Run; 111–130 checks unqualified non-draft Task BLOCKED.

Thus a **configured and uniquely bound but not yet runtime-qualified model** is compatible with a Draft `goal.start`, once a genuine resolver/host route exists. A project-level typed `goal.start` with **no model configuration** is not supported by the current response/session contract. The independent domain API is broader: `spec/v2.0/contracts/openapi.json` defines `POST /v1/projects/{project_id}/goals` (`createGoal`), and `internal/domain/operations.go:165–187` creates a DRAFT Goal without consulting model/runtime. It requires accepted Requirement refs and a valid acceptance contract; it does not mint the typed CLI session snapshot.

## Precise answer on an empty coordinator configuration

A JSON config file `{}` may get past the narrow constructor route loop because `apps/control/main.go:222–230` fills `data_root`, `api_url`, and host authorities; `runtime_coordinator_windows.go:91–157` validates loopback/data-root and iterates only configured routes. This is **not** a Goal binding resolver with a selected model. With an empty `routes` array, `ResolveGoalBinding` has no model: `runtime_goal_bindings_windows.go:49–65` first tries a current typed configuration head, but even if one exists `ValidateBinding` calls `sessionModel`, which needs a matching configured route/profile (`runtime_sessions_windows.go:11–50,162–177`). With no head, `runtime_goal_bindings_windows.go:75–114` enumerates zero routes and returns `MODEL_UNAVAILABLE`. Empty `providers` by itself is not an execution authorization or model configuration. The coordinator also runs `Recover`/`Scan` (`runtime_coordinator_windows.go:189–238`); a config file is not a passive Goal-only resolver. No actual empty-config Host was launched in this investigation, so constructor/startup viability is source inference only.

For a real Draft in the current CLI contract, there must be exactly one authenticated active workspace and a selected nonempty model ref. A route-based selection requires `RuntimeCoordinatorConfig.routes[]` (`project_id`, `runtime_id`, `executor_id`, `executor_token`, `command_id`, absolute `executable`, optional `bundle_file`) and scheduler authority at constructor time (`runtime_coordinator_windows.go:30–50,143–176`); `sessionModel` then requires a genuine `RuntimeRegistration`, current `runtime_bindings` to a sealed/effective profile Artifact, Mu `model_config.ref` plus exact command (`runtime_sessions_windows.go:11–50`, `runtime_qualification.go:173–214`, `runtime_goal_bindings_windows.go:76–118`). `validateRuntimeModelConfig` requires backend Mu; `model_config.api=openai-completions`, model/provider/ref/route/endpoint, bounded max output/calls, frozen tools, and bundle hash (`runtime_model.go:51–85`). It does not require a qualification result; optional `model_qualification`, if present, must bind exactly (`runtime_model.go:87–96`).

When the Owner has created a typed `host.configure` head, `ResolveGoalBinding` selects that ref (`runtime_goal_bindings_windows.go:49–65`), then `sessionModel.matchStoredClientConfiguration` additionally demands matching endpoint/provider/model, non-null actual protected credential ref, and a matching `providers[]` MODEL route with exact credential ref/revision/model config (`runtime_sessions_windows.go:53–100`; provider JSON fields in `runtime_broker_windows.go:24–40`). `host.configure` itself checks real host credential metadata/status when a credential ref is supplied (`client_protocol_configuration.go:498–528`); it need not call the provider merely to store config. Therefore the clean bootstrap choices are either a real route/profile without a typed head (legacy-compatible path), or a real typed configuration **and** matching route/profile/provider metadata. Neither is an empty coordinator config. Draft `goal.start` itself stays zero-provider because `buildFiniteClientGoal` returns before Task/admission; any zero-provider claim for the whole Host must still verify no other ready work was scanned.

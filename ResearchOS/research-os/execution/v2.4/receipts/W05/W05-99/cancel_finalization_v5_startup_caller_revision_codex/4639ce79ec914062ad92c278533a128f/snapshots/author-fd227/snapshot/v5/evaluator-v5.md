# v5 exact evaluator amendment — proposed, unexecuted

This is part of the complete v5 closed contract, replacing only the ambiguous multiset and all-epochs-as-birth rules in v4. No producer order, numbered SQL, SDK or public schema is changed. All future acceptance controls below are NOT_RUN. These are proposed private witness fields, not frozen public fields. The revised view has **34 categories**, with its original 32 positional tuples unchanged.

## R1: references are a multiset, not unique edges

The category registry records the actual table key for each category. Only categories with an actual declared PK/UNIQUE key reject repeated keys; a duplicate key with equal bytes also fails the source wire, rather than being silently folded. `domain_refs` has no PK or UNIQUE and is explicitly MULTISET. SQL uses UNION ALL and json_group_array without DISTINCT. Preserve each occurrence of its exact 9-column tuple. No invented rowid, occurrence ID, deduplication or new producer constraint is introduced.

For each referenced owner version, strict-decode its actual raw bytes, validate the frozen entity schema, recompute receipt/content hash by the original rule, and enumerate reference occurrences using the exact store.refs/relationKind traversal. Skip id/project_id; supersedes_id/parent_policy_id rules remain; relation arrays emit one occurrence per element at the SAME field path; ordinary nested arrays use indexed paths. A VersionRef occurrence supplies exact entity/id/revision/nullable hash. An ID-only relation supplies target kind/id and occurrence count but **does not encode its historical target revision**. Never invent that revision or substitute a later head. Resolve its actual retained relation tuple to the exact immutable target version; repeated same-owner/same-field/same-ID occurrences must have the same captured target tuple, since the original producer resolved that target under one Tx. The global parent-policy fallback is the exact original project/global relation, not an arbitrary cross-project exception.

Two-way matching consumes one stored occurrence for each schema-derived occurrence. Missing, surplus or wrong field/kind/id/count fails. Explicit VersionRefs must match revision AND actual nullable content_hash. ID-only historical relations must resolve an existing typed target version; their actual revision, target raw-byte digest and nullable hash are captured, not claimed to be reconstructible from the bare ID alone. Historical validation compares that exact captured tuple and target body/hash. A legal dependency_task_ids=[X,X] produces two equal /dependency_task_ids rows: count 2 is valid, count 1 or 3 is invalid. Distinct nested-array indices remain distinct fields. dependencyVector's ordered refs array also preserves repetitions; it is not a set.

Both ADMITTED_MEMBER and FINALIZED_MEMBER add exactly one required field `reference_closure`: sorted array of closed objects `{owner_project,owner_ref,owner_body_digest,rows,targets}`. owner_project is the actual owner domain_versions project (member project, or the original permitted global-policy empty project); owner_ref is exact VersionRef; owner_body_digest=R(actual domain_versions.body bytes). rows is the lexicographically sorted expanded array of all actual 9-column domain_refs tuples for that owner; equal tuples remain repeated. targets is the sorted unique array of `{project,version_ref,body_digest}` for every row target, containing the real nullable hash and raw-byte digest. The complete owner closure follows the finite set of references named by the member/proof, with visited VersionRef identities breaking cycles, not dropping repeated edges. Pins are a unique set of owner/target versions; rows are a multiset. Membership GroupHash remains a unique Task set. These three concepts must not share a generic dedup helper.

Origin `source_closure` uses the identical reference_closure shape plus an exact sorted version-anchor set. At admission/origin creation the evaluator independently checks the body-derived occurrence shapes and captures all target versions as above; at later validation it re-enumerates source rows and demands exact multiset equality to the immutable captured rows plus target raw digests. No claim is made that an ID-only pre-proof target revision can be authenticated against a missing historical capture. Complete hostile rewriting of all pre-anchor canonical history is outside the v4/v5 consistency guarantee. A target revision/hash alteration after its admitted/origin anchor, an explicit VersionRef mismatch, or any multiplicity alteration fails. This boundary must be visible in tests and backup reporting.

Ref writes are blocked once the owner is pinned by an admitted/final group OR appears in an immutable origin reference_closure. This preserves s.put->s.refs before the first proof; legal duplicate rows can be inserted before proof capture. Do not protect domain_objects against its legitimate UPSERT. Do not add global uniqueness to domain_refs.

## R2: permanent birth plus one immutable origin per dispatch epoch

Keep f08_dispatch_origins PRIMARY KEY(project,run_id,epoch), unique dispatch_key. Every post24 Run dispatch gets one origin; every old23 cohort Run is excluded at every epoch. Mode8 derives from the just-inserted PREPARED tuple plus already stored source rows. Mode2 checks that full derived document at insertion. It must not require the future RUN_CHANGED for a rebuilt epoch. Historical origin validation (called from proof/final/backup evaluation) resolves the captured immutable versions, not current mutable heads or a still-PREPARED current state; dispatch state may advance only by the original monotonic rules.

`format,project,run_id,epoch,dispatch_key,manifest_digest,manifest_bytes_digest,birth,epoch_authority,source_closure`.

## Current epoch cancellation and historical validation

NEVER_LAUNCHED_NATIVE means the admitted **selected epoch** never launched, not that this Run never had earlier process execution. For first epoch prior_epochs is empty. For later epoch bind and revalidate the admitted origin's complete settled prior_epochs; preserve its actual earlier processes/effects/observations. Current selected dispatch must still be original PREPARED with empty worker/locator/identity and zero observation sequence/hash. A carried checkpoint/use/upload explicitly proven by that epoch's checkpoint_carry is allowed as pre-launch input; any other current execution upload, native observation, process identity or SDK delivery contradicts never-launched. Never fabricate an empty-SDK/process proof for earlier epochs.

FINALIZED_MEMBER adds `prior_epoch_closure` (exact origin.epoch_authority.prior_epochs, [] on first epoch/noRun) and `prelaunch_checkpoint_carry` (exact carry row anchor or null). Its effect_closure enumerates all Run-wide obligations through the admitted epoch, preserving actual per-row epoch and original request/reservation/cost bindings. Its selected epoch field remains the admitted epoch. NO_EXECUTION uses []/null. TRUSTED_STARTED_TERMINAL still requires real selected-epoch native/process/SDK evidence. Unknown costs stay unknown; local-launch classification never whitelists a MODEL obligation.

Creation-time checks use actual heads; historical backup/finalized replay uses exact captured immutable versions/rows. No later current Run/Task/Session/fence substitutes. Before actual mutation/finalization require RunID+epoch/Task ownership still equals admission; an intervening sameRun newepoch fails stale ownership instead of cancelling it. Different later Run also remains untouched. A completed response is historical byte replay. If cancellation wins first, existing stop guards block resume/switch; if a legitimate rebuild commits first, a stale old-epoch CANCEL cannot acquire new epoch authority.

Old23 cohort exclusion remains project+RunID permanent and forbids every origin for that Run. Existing legitimate recovery/switch still runs unchanged original Go admission and SQL monotone dispatch rules; it cannot use never-launched fast finalization. No original ACK/header/witness backfill. No new24 missing origin can be reclassified into this cohort.

## Historical prefixes versus newly appended facts

An epoch origin captures the actual source prefix at dispatch insertion. Its immutable references/raw digests must continue to exist exactly. Historical backup does not require that no later lawful observation/effect/cost/domain version was appended. For every captured effect prefix require exact original key/sequence/raw bytes and complete ordering; validate subsequent rows under the existing monotone effect rules. At finalization enumerate the complete current Run-wide effect/reservation/cost set through the admitted epoch again, including late actual costs, rather than treating the captured origin array as the whole current inventory. No deletion, replacement, missing original reserve or unresolved UNKNOWN is excused by this prefix rule. An origin is evidence of original admission, not a final accounting acceptance or permission to release unknown exposure.

# Existing sandbox child/pipe drain activation blocker

Read-only review of Main `001f7e5a4d95152c8f83874a60d9fbd3bbace538`. No source edits, tests, native processes, models, databases or qualification. This is outside the proposed six-path candidate-capture scope.

`ops/experiment_sandbox/sandbox_windows.go:343` stops its process/deadline polling loop as soon as the top process exits. It waits at most about 500ms for the whole Job (`:368-374`), records `Stopped` and then waits synchronously for both pipe readers (`:376`). A surviving Job child can retain a pipe write handle without closing it. No subsequent context/deadline polling or Job termination occurs on that path. The deferred Job close (`:212`, configured KILL_ON_JOB_CLOSE at `:214`) cannot run until these reads return. `Process.Cancel` only cancels context and closes input (`async_windows.go:162`); it does not directly terminate this already-draining Job. This is a concrete control-flow risk, not a claim that a native reproduction was run.

The old `Run` is already `Start(ctx)` followed by `Wait(context.Background())` (`sandbox_windows.go:84-89`). The candidate slice should keep this ownership behavior. Replacing it with `Wait(ctx)` would instead allow the Host's deferred staging cleanup to race a live sandbox, because `Wait` returns an empty receipt immediately on cancellation (`async_windows.go:164-171`). A new cleanup timeout is not a substitute for terminating and observing the actual Job.

The smallest separate lifecycle source scope is `sandbox_windows.go`, and, only if needed for safely coordinated cancellation/draining, `async_windows.go`, plus focused tests in the existing sandbox package. Keep the existing public Command/Receipt wire and complete-wait contract. After top-process exit, if Job accounting still has active descendants, terminate this owned Job and observe zero active processes before successful completion. Context/deadline and stream failures must remain actionable during drain. A drain failure must make the receipt unusable, never synthesize stopped/drained/cleanup success. Preserve original exit/timeout classification explicitly when descendant cleanup is forced.

Pure fixtures can exercise an extracted package-private lifecycle decision/coordinator using injected Job-accounting, terminate, wait, stream-result and time/cancel operations: parent-exit with active child; no child; child exits during grace; held stdout/stderr; cancellation before/during drain; termination/accounting/wait error; either stream error; cleanup failure; and shutdown ownership (no operations after handle close). Do not add a public fake-native seam or infer real Windows cleanup from mock success. If keeping tests outside lifecycle production interfaces is easier, overlay-only tests may cover a small internal coordinator, while actual handle behavior remains unqualified.

Later separately authorized native validation must demonstrate an actual descendant that inherits and retains stdout/stderr after parent exit, cancellation/timeout during drain, Job-zero observation, EOF/stream limits, no surviving owned child, and staging/profile/handle cleanup with exact receipts. The `CleanupComplete` flag currently measures staging `RemoveAll` only (`sandbox_windows.go:154-157`); deferred `DeleteAppContainerProfile` and `CloseHandle` return values are not represented as verified success. No new guarantee should be claimed for those actions without corresponding implementation and evidence.

Also bound `BeforeResume` work itself: command timeout starts after Resume (`sandbox_windows.go:337`), so it cannot bound a stuck callback. The candidate helper should use finite file/entry/byte budgets and check context without adding native or lifecycle behavior to its six-file scope.
